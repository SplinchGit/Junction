## Subscription access and billing

- **Codex.** OpenAI documents ChatGPT sign-in for subscription access, non-interactive CLI operation, and App Server account and rate-limit reads and notifications. API-key billing is separate. Purchased credits and credit-based workspace plans also exist. A ChatGPT account type or a below-threshold rate window alone does not establish that the next run is restricted to included allowance. Enterprise access tokens have a separate eligibility and administration path. [Authentication](https://developers.openai.com/codex/auth), [Non-interactive mode](https://developers.openai.com/codex/noninteractive), [App Server](https://developers.openai.com/codex/app-server), [Pricing](https://learn.chatgpt.com/docs/pricing)
- **Claude.** Anthropic documents non-interactive `claude -p` and distinguishes an end user signing into their own unmodified Claude Code binary from a third-party service routing users' subscription credentials. Product distribution has separate terms. Anthropic also documents that account usage credits can carry the same Claude Code session into separately billed usage. The CLI sign-in result used by Junction does not prove that usage credits are disabled. The audit did not establish a supported preflight that guarantees included-only consumption for every unattended run. [Programmatic Claude Code](https://code.claude.com/docs/en/headless), [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance), [Usage credits](https://support.claude.com/en/articles/12429409-manage-usage-credits-for-paid-claude-plans)

The live acceptance blocker is evidence of included-only execution for the actual account and workspace on each provider. A future dispatch gate needs to distinguish account sign-in, known included allowance, verified spending controls and unknown billing state. The engineering path also needs to classify auth and provider failures separately from quota exhaustion. Provider-reported windows and native client status should remain the source of capacity evidence.

## First implementation increment

When Claude rejects a turn after a Codex handoff, Foreman now keeps the handoff checkpoint and schedules the earlier of the two provider checks. For a reported reset it keeps a one-minute buffer. With no usable Claude reset it uses a 30-minute recheck, matching the existing coordination fallback. The saved Claude snapshot suppresses another automatic probe during that interval, including after an explicit recheck of Codex. Foreman treats an expired Codex capacity window as unknown and checks the saved source fingerprint before either provider resumes a handoff. This increment uses the existing executor, scheduler, store and lock.

The regression drives a real temporary Git checkout through Claude rejection with each provider resetting first, an unknown-reset rejection, an early recheck and subsequent Codex resumption of the same task. It checks that the rejected turns leave the source untouched and the resumed turn produces verification evidence with canonical HEAD intact. Provider responses and command execution in this regression are fixtures. The separate coordination rehearsal also uses fixture providers.

## Remaining acceptance sequence

1. Establish and enforce included-only dispatch for each account before additional unattended live testing. Surface unavailable or unverifiable access as an actionable provider state.
2. Reuse the saved Foreman and task records for independent provider status and bounded rechecks. Preserve Pause and Stop across restarts. Agree which previously authorised waits may restore automatically and which interrupted turns require reconciliation.
3. Exercise real provider quota and recovery in both directions with one writer, explicit owner decisions and a review of the exact canonical diff. Record billing evidence alongside the execution receipts.
4. Run the paired Android task, voice and notification cycle under offline, locked-device and host-restart conditions. Use those results to drive the memory, voice and initiative increments before the multi-week integrated run.
