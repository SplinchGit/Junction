# Junction World: security and setup

## Current deployment

Junction World is installed and running. See [PERSISTENT-RUNTIME.md](PERSISTENT-RUNTIME.md) for the current architecture, security boundary, owner commands, verification results, and limits. The installation notes and checklist below describe the original provisioning procedure; dated readiness statements and uncompleted items in that checklist are historical and are not the current VM status.

## Official downloads

- Install Oracle VirtualBox for Windows only from [Oracle's VirtualBox downloads page](https://www.virtualbox.org/wiki/Downloads). No Extension Pack is required.
- Download the amd64 `netinst` image from [Debian's official netinst page](https://www.debian.org/CD/netinst/). Verify the image using the SHA-512 checksum and signature published alongside the image, following [Debian's image verification guidance](https://www.debian.org/CD/faq/).
- The setup script does not download software, change Windows Firewall, start a VM, or install software on Windows. Review the script, then run it in PowerShell after installing VirtualBox.

## Create the VM

From the repository root in PowerShell:

```powershell
.\scripts\windows\New-JunctionWorldVm.ps1 -DebianIso 'C:\path\to\verified-debian-amd64-netinst.iso'
```

The script creates `junction-world` with two CPUs, 2048 MiB RAM, one 16 GiB dynamically allocated VDI, and one NAT adapter. It turns off clipboard, drag-and-drop, USB controllers, audio, recording and VRDE. It creates no host shares, port forwarding, host mounts, or Guest Additions. The VM remains powered off with its virtual network cable disconnected. Use `scripts/windows/Start-JunctionWorld.ps1` to boot it. The launcher temporarily holds the cable down until the live VirtualBox NAT engine confirms localhost reachability is disabled. It permits either no port forwarding or the one exact loopback-only audit forward. During initial Debian package installation, internet and LAN egress can be enabled by NAT; the autonomous runtime must not be installed/resumed until the guest firewall is active and verified.

Guest Additions were found active in this already-installed VM. The owner explicitly chose to continue with them present. Do not enable clipboard, drag-and-drop, shared folders, USB, or other convenience features. The runtime has no dependency on Guest Additions, and no Guest Additions API is used by the host relay. Their installed kernel modules and services remain an additional attack surface and are included in the residual risk. If they are later removed, verify facilities and kernel modules are inactive after a full reboot.

In Debian Installer, use a minimal text install: **SSH server: off**, **standard system utilities** only, and no desktop environment. Create a separate administrator account for maintenance. Do not place personal or Junction provider credentials in Debian. The current VM has a 10 GiB partition table on the enlarged 16 GiB VDI, so verify the root filesystem layout and expand its available filesystem space using Debian's official `cloud-guest-utils`/`growpart` and filesystem tools only when the root partition is the final partition. If swap or LVM layout prevents safe expansion, stop and inspect the layout before changing partitions. Confirm at least 10 GB free on the guest filesystem before proceeding.

The read-only ISO at `artifacts/junction-world-provisioning.iso` contains the current runtime and firewall files. It was created from `scripts/junction-world` and includes a SHA-256 manifest. It is attached to the VM's DVD drive. From the Debian console, log in as the maintenance administrator, become root, install Debian's official `python3`, `nftables`, `util-linux`, and `cloud-guest-utils` packages, then follow `INSTALL.txt` on the disc. `expand-guest-root.sh` only grows a direct ext2/3/4 or XFS root partition when it is already the final partition; it refuses LVM, encrypted, RAID, and layouts with a following swap/data partition. Confirm its `df` output is at least 10,000,000,000 available bytes. If it refuses, no partition changes were made; inspect that specific layout before proceeding. `harden-guest.sh` creates `/home/junction/junction/{identity,memory,goals,projects,journal,logs,state}`, installs the root-owned services/firewall, caps system journal use, and enables only the root supervisor. The host-owned pause starts on. The autonomous heartbeat unit is not started by setup. No token or provider secret is copied to the guest.

The firewall allows only DHCP during boot, DNS to VirtualBox NAT DNS for the fixed research broker, HTTPS from the dedicated research UID to short-lived public Wikipedia IP entries, and a host-initiated service on `10.0.2.15:43130`. It blocks guest-originated access to Windows/LAN ranges and all other guest egress. `apt` is used before enabling the firewall, from official Debian repositories. Do not weaken the rules for package installation, downloads, or arbitrary browsing.

## Network boundary

VirtualBox NAT is the only adapter. Do not use bridged networking, host-only networking, or internal networking. Oracle documents that NAT guests can address host loopback through `10.0.2.2`; therefore NAT alone does **not** isolate host services. On this VirtualBox 7.2.20 installation, earlier VM starts logged `LocalhostReachable=1`, even though the VM was intended to use `off`. A guarded launcher is provided because this value differed across observed starts and powered-off configuration reads. Use `scripts/windows/Start-JunctionWorld.ps1` for every start. It checks static settings, sets the virtual cable disconnected, applies `--nat-localhostreachable1 off`, starts the VM, verifies the live NAT engine reports `0`, and only then connects the cable. If it cannot verify `0`, it leaves the cable disconnected and does not enable guest networking. Do not start the VM directly through VirtualBox Manager until this behavior is resolved and reverified. The guest nftables rules are a second, agent-independent block on access to `10.0.2.2` and other private/reserved ranges; do not start the autonomous heartbeat until those rules are installed and verified. Never enable localhost reachability: it could expose every Windows service listening on loopback, including Ollama, to the guest. Do not run a host listener on a wildcard or LAN address.

The two VM-to-Windows information flows are validated audit events and bounded prompts/responses on a fixed localhost Ollama inference route using `qwen3.5:2b`. The inference route cannot select a model, call tools, reach other Junction APIs, or log prompt/response content. Windows polls through one NAT forward bound only to `127.0.0.1`; the guest API has fixed routes for audit, inference, host messages, and acknowledgements. It has no command, filesystem, general RPC, proxy, credential, environment, or VBoxManage route. The host-issued pause and heartbeat controls are sent with that poll. This fixed HTTP route is unauthenticated inside the guest network; its safety depends on the VirtualBox NAT mapping being bound only to Windows loopback and the guest firewall accepting TCP 43130 only from NAT gateway `10.0.2.2`. Do not widen that binding or guest firewall. The Android app talks to Junction for Windows over its existing paired certificate-pinned LAN protocol; no Firebase relay changes are included.

The guest research fetcher is restricted to three Wikipedia text search results using a pinned, validated public IPv4 address, TLS hostname verification, no redirects, JSON-only response type, strict response size limits, and short timeouts. The agent itself and the separately executed project-code UID have no network egress. The project-code UID cannot access the supervisor's Unix socket. No arbitrary URLs, downloads, archives, packages, scripts, or binaries are supported.

## Host boundary and audit path

The VM cannot access Windows files, credentials, environment variables, provider secrets, arbitrary Windows commands, or VBoxManage through its configured guest interface. Do not add general RPC, arbitrary HTTP proxying, host file reads, shell execution, host tool invocation, or a writable VirtualBox control endpoint. The explicit inference exception carries bounded prompt/response text to and from Ollama; it is not copied to the host audit store. Other VM-originated data copied to Windows is limited to schema-validated audit events. The separate host audit history appends validated events; Android stores copies with insert-ignore semantics and exposes no update/delete DAO. The guest receives no path to prior host audit records.

Android reads host-confirmed VM status, audit history, pause/resume, heartbeat interval, and the bounded World chat through the existing certificate-pinned, paired Junction LAN connection. Owner messages are recorded as `COMMUNICATION` audit events and placed in a host-owned bounded queue; the host delivers them on its next poll. Junction replies appear as VM-generated `COMMUNICATION` audit events. World messages are not added to Firebase chat sync. No Firebase relay changes are part of this design. If a phone is not paired to the Windows Junction installation over the local trusted network, the Audit tab reports World unavailable.

Pause is host-owned and starts enabled. The Windows relay sends a fixed control heartbeat every 2 seconds while the guest is online, separately from longer inference polls. The guest supervisor treats loss of that heartbeat for 15 seconds as a pause, persists that pause, and stops the active bounded heartbeat and child sandbox units. The root supervisor uses a serialized, bounded wake request to run queued Android messages after an active wake finishes. No VM service can write Windows controls. A pause delivered through Junction's paired Android control is authoritative to the guest.

## Guest runtime requirements before enabling it

The scheduler waits between events and starts with a configurable 10–20 minute heartbeat. It does not continuously call the model and skips inference if no relevant state changed and there is no active goal or owner message. A failed root supervisor is limited to five starts in five minutes with a 30-second restart delay. Inference/tool/iteration counts, context, subprocesses, network requests, runtime, logs and disk consumption are bounded. The agent runs as `junction`; the root supervisor, egress firewall and host audit trust are outside its write access. Project Python runs under a separate `junction-code` UID in a transient systemd unit with CPU, memory, process, file-size and wall-clock limits, read-only project files, small bounded temporary filesystems, no access to the supervisor socket, and no network. Junction's file tools are the path for persistent project changes. Warning/critical storage thresholds stop storage-heavy activity. Guest Additions are present in this VM by owner choice, although not needed by the runtime.

Untrusted agent-written code can still damage or encrypt its own guest files, exhaust guest resources despite limits, or exploit a Debian/kernel/VirtualBox vulnerability. Text from public websites can contain prompt injection. Host and Android audit summaries are untrusted display data even after schema validation. VirtualBox is a strong isolation boundary, not a proof of perfect containment.

## Verification before start

Keep the VM powered off until the checks below are run and the results recorded. Do not mark it ready based on configuration inspection alone.

- [ ] Host OS is Windows 10 Home; official Oracle VirtualBox is installed; `junction-world` has 2 vCPU, 2048 MiB RAM and one dynamically allocated 16 GiB VDI; the guest root filesystem shows at least 10 GB free after Debian/runtime installation.
- [ ] One NIC is NAT; no bridged/host-only adapters, shared folders, USB controllers/passthrough, host mounts, webcam/microphone passthrough, audio, VRDE, clipboard, drag-and-drop, or screen recording are enabled. Guest Additions are currently present (accepted residual risk), and all convenience channels remain disabled.
- [ ] Debian minimal install boots as `junction`; workspace persists after a full guest reboot; ownership and permissions prevent the agent from changing supervisor, firewall, credentials or audit trust.
- [ ] From the guest, host Windows directories, user directories, clipboard, shared folders, USB devices, host credentials, Junction secrets, VBoxManage and arbitrary host services are inaccessible. Private LAN, loopback, link-local, multicast and reserved network destinations are blocked.
- [ ] Start the VM with `scripts/windows/Start-JunctionWorld.ps1` and retain its output. Verify the live VirtualBox log and `showvminfo --details` report `LocalhostReachable: 0`. If not, disconnect the virtual cable and stop. Verify guest nftables drops traffic to NAT gateway `10.0.2.2`, private, link-local, multicast and reserved ranges. After the guest firewall and supervisor are installed and these checks pass, configure only `VBoxManage controlvm junction-world natpf1 "junction-world-audit,tcp,127.0.0.1,43130,10.0.2.15,43130"`. Verify Windows listens on loopback only and no public/LAN listener exists. Test that no guest-originated connection reaches Windows ports. Malformed, oversized, replayed and unknown requests are rejected and appear as bounded security audit records. No host command, file, environment, credential, proxy or unrestricted RPC route exists.
- [ ] The reviewed research path can fetch Wikipedia public text only; attempts to download binaries, archives, scripts, packages, follow redirects, use arbitrary URLs as a proxy, or reach private addresses fail and are audited. Project code cannot write outside its bounded temporary filesystems.
- [ ] Public research access works through that narrow path. No general guest internet egress is enabled.
- [ ] The only model path is the fixed local Ollama model through the bounded inference relay; model selection and tools are unavailable, and prompt/response content is not retained in Windows audit logs. No Junction provider/API secrets are present in the guest.
- [ ] A test wake occurs; idle CPU falls to negligible levels; pausing blocks new inference and interrupts bounded work; resume works only from the paired Android control; heartbeat changes persist across restart. Verify local Ollama is available and fixed to `qwen3.5:2b`.
- [ ] Iteration/tool/runtime/subprocess/network/log limits work; duplicate event IDs are idempotent; malformed audit objects fail validation; guest disk warning and critical thresholds work and critical state prevents storage-heavy work.
- [ ] The guest cannot alter prior Windows audit records; Android receives the appended records, escapes hostile strings, searches/filters them, retains history across app restart, and displays failures/denials.
- [ ] Confirm the Windows/Android Junction features outside this work still operate, and record the VM state plus the verification date before starting autonomy.

## Manual start and recovery

Only after all checks pass, start the VM with `scripts/windows/Start-JunctionWorld.ps1`; it guards NAT localhost isolation before bringing up the virtual cable. The VM has no host-management endpoint and cannot start, stop, or resize itself. To stop the experiment, use Android Audit **Pause** first, then shut the VM down from VirtualBox Manager. On host restart, keep the VM paused until host Junction and its audit bridge are available. Inspect the Audit tab for host-confirmed actions, errors, resource warnings, and security denials; use Advanced host logs for transport diagnostics.
